## 二、只读检查结论

| 检查项 | 结论 |
|---|---|
| 技术栈 | Vite 5 + React 18 + @supabase/supabase-js 2.x |
| 生产构建 | `vite build`，`base: './'`，资源全部为相对路径 `./assets/...` |
| 服务端依赖 | **有**：`/sb` 同域代理（Netlify Function / EdgeOne Edge Function），转发 `auth/v1/*` 与 `functions/v1/api/*` |
| 客户端路由 | **无** react-router、无 `pushState`；分享用 `?t=<token>` 查询参数 |
| 刷新是否 404 | 不会（单一入口，无 path 路由），**无需 SPA fallback** |
| Supabase 配置项 | `VITE_SUPABASE_URL`（缺省 `origin + /sb`）、`VITE_SUPABASE_ANON_KEY`、`VITE_API_BASE`（缺省 `origin + /sb/functions/v1`） |
| 硬编码域名 | 无。源码中只有注释提到 `supabase.co`，构建产物不含 Netlify / workers.dev 域名 |
| 服务端密钥 | 未发现。产物中仅有 publishable key；`sb_secret_` 仅出现在 SDK 的字符串判断逻辑里 |

## 三、关键兼容性问题

**秒哒是纯静态托管，没有 `/sb` 代理。** 当前产物在运行时会请求：

```
https://<秒哒域名>/sb/auth/v1/...          ← 匿名登录、token 刷新
https://<秒哒域名>/sb/functions/v1/api/... ← 激活、开始测评、提交计分
```

两点会导致功能不可用：

1. 秒哒域名下不存在 `/sb`，请求返回 404 → 兑换码验证、扣次、结果读取全部失败。
2. 页面本身能打开（静态资源是相对路径，不依赖根域），但打开后会卡在“开启殿门”。

已实测：把 `https://gongdou-test.netlify.app/sb/...` 当跨域后端调用**不可行**——`OPTIONS` 预检返回 204 但**没有 `Access-Control-Allow-Origin` 头**，浏览器会直接拦截。

## 四、三种可选处理方式

### 方式 A：秒哒支持反向代理 / 云函数（推荐验证）
若秒哒提供函数或代理能力，把 `/sb/*` 转发到：

```
https://juiaetgiyltpbmmvctdc.supabase.co
```

白名单前缀：`auth/v1/`、`functions/v1/api/`；需转发请求头 `authorization`、`apikey`、`content-type`、`x-client-info`。这样当前 ZIP 可**直接使用，无需重新构建**。

### 方式 B：构建时直接连 Supabase（仅境外网络可用）
```bash
VITE_SUPABASE_URL=https://juiaetgiyltpbmmvctdc.supabase.co \
VITE_API_BASE=https://juiaetgiyltpbmmvctdc.supabase.co/functions/v1 \
VITE_SUPABASE_ANON_KEY=sb_publishable_... \
npm run build
```
缺点：`supabase.co` 在中国大陆被墙，国内访客会在登录环节失败。

### 方式 C：后端迁移到国内
静态站 + 国内函数 + 国内数据库，才能同时满足“秒哒托管 + 国内可用”。工作量最大。

## 五、需要在秒哒验证的配置

1. 解压后 `index.html` 是否在根目录，`assets/` 是否同级（ZIP 已按此结构打包）。
2. 站点访问是否走子路径；若是，确认相对路径资源能正确加载。
3. 是否存在固定域名/根路径假设（当前构建无此假设）。
4. 是否支持函数或反向代理，能否配置 `/sb` 转发（决定方式 A 是否可行）。
5. 是否支持自定义响应头（需要 `cache-control: no-store`，避免兑换码校验结果被缓存）。
6. 是否支持 HTTPS（Supabase 认证要求安全上下文）。
7. 发布后实测：匿名登录 → 输入兑换码 → 答题 → 结果 → 分享链接。
